# 执行可靠性：问题总结与集成约定

[English](EXECUTION_RELIABILITY.md) | **简体中文**

本文是通用工程问题总结，不是实盘事件日志。示例与测试均使用合成数据，不包含私有策略、
账户历史、凭证、生产风控阈值或部署配置。这些组件是库接口，不是开箱即用的交易服务，
也不代表获得了交易授权。

安装开发依赖后，可运行无凭证接线示例 `python examples/offline_execution_recovery.py`。
它仅使用临时状态和合成回调；生产环境的审计记录必须持久化。

## 已处理的问题

| 故障模式 | 开源侧处理 | 回归覆盖 |
|---|---|---|
| FILLED 确认先于完整成交字段或订单查询索引到达 | 合约适配器先查已确认订单，再查确定性客户端 ID；最多七次只读查询，绝不重复下单。 | `test_filled_order_confirmation.py`：延迟可见、耗尽、身份不符、限流、传输错误 |
| 不同传输版本的 SDK 拒单字段有变化 | 只有白名单内的错误码/消息组合才判为明确拒单，兼容当前交易所数字错误码；其他错误仍须核对。 | 覆盖当前数字错误码及旧式 HTTP-400 形式。 |
| 成交历史与实际仓位不同步 | `FillConfirmation` 只允许在已确认成交证明的精确数量变化范围内有限等待。 | `test_fill_confirmation.py`：加仓、减仓、全平、超额成交、外来合约和方向 |
| 第一次刷新清空 dirty symbols，但成交历史仍未更新 | 保存不可变的受影响合约集合，每次重试都传入同一范围。 | 保持查询范围，直到精确确认。 |
| 修复最后一步在下单后耗尽请求预算 | `RequestBudget` 在获取账户锁之前预留整次操作预算，包含最终全量结算和第二次账户快照。 | `test_request_budget.py`：完整预算、竞争、重启、过期、策略不一致 |
| 结算分批到达导致过早永久故障 | `SettlementGate` 仅针对明确的 `ValuationPending` 持久化有限暂停；订单或归属不明仍立即故障。 | `test_settlement_gate.py`：重启不重置期限、完整核对、永久故障、时钟回退 |
| 把共享归属问题或不确定写操作误当成可重试网络错误 | 已有虚拟归属和组合状态保存确定性订单身份，恢复必须查询。 | 组合协调器、虚拟路由、恢复与账户锁测试 |

## 集成顺序

1. 计算保守的完整请求权重：预检、所有可能的成交确认查询、恢复查询、最后的全量结算和
   第二次账户快照。权重及额度必须按实际端点和共享 IP 审核。
2. 在 `SharedAccountTurn.acquire()` **之前**调用 `RequestBudget.reserve(weight)`。
   不足时在锁外延后，保持监督进程心跳，并采用经过批准的总等待时限；不要持锁忙等或休眠。
3. 在账户锁内，每次请求前扣除 permit 权重，包括重试查询。配置有限网络超时，禁用自动
   重试写操作。在新增风险前核对完整账户、归属、批准、停止状态和保护措施。
4. 下单前持久化意图和成交路由。下单结果不明时必须查询原始身份，不能因超时而补一笔订单。
5. `FillConfirmation.confirm(before=..., expected=...)` 的数量来自**已确认累计成交**，
   不能来自目标仓位。刷新回调必须查询传入的全部合约，即使其他组件已经清空 dirty set。
   通过必需的审计回调持久化每个 `ConfirmationAttempt`。
6. 用 `SettlementGate.reconcile(full_read_only_check)` 核对结算。只有订单与归属已经证实，
   剩余问题明确只是结算估值差异时，才抛出 `ValuationPending`。等待期间接口抛错并阻断
   交易，不豁免金额差异。只有全量核对成功才能解除临时等待；不会解除已有故障或人工停止，
   成功也不等于交易授权。

以上步骤需要应用层接线。组合协调器不会自动启用新增门禁，这些接口也不会启动进程或更改
账户。结算等待不能替代紧急风险处理：后者须另行批准，不能假定未核实的数量或盲目发单。

## 边界与持久化

- FILLED 字段不完整时，最多七次查询，总计划退避时间 14.5 秒；每次网络读取还须由调用方
  配置超时。仅明确的 `-2013` 订单索引暂不可见错误可以重试，其他错误保持不确定状态。
  恢复结果必须匹配合约、交易所订单 ID、客户端 ID、买卖方向、持仓方向和申请数量，并具有
  精确的 FILLED 成交数量及有效成交价。
- 仓位确认默认最多三次观察，重试准入窗口为五秒；不会强行中断正在进行的回调 I/O。
  额外仓位、无关变化、重复行或超出已确认变化范围的数量立即失败，不用舍入容差掩盖归属差异。
- 同一共享限额范围使用一个本地 SQLite 请求预算数据库，重启后保持相同容量和窗口。
  一次预留完整操作，由进程内 permit 逐次消费。permit 有效一窗口，预留保留两窗口，
  以保守计入临近过期才发出的请求。未用额度不退还，因此吞吐可能低于交易所上限。
  permit 过期不能发请求；重启后必须重新获取预算并核对状态。相关进程都要接入，不支持跨主机协调。
- 结算门禁使用独立本地 SQLite 数据库。调用方指定最大等待时间，持久化后不可静默改变。
  首次等待时间跨重启保留；到期、时钟回退和无关错误会持久化故障。使用固定状态路径及严格的
  操作系统权限。不得通过删除、重建数据库绕过故障；恢复必须审核交易所证据。

## 不应变成通用策略默认值的经验

- 强平必须按实际成交、费用和仓位归属核对，不自动意味着允许重新开仓或平掉所有策略。
  杠杆、逐仓、冷却期、继续运行与亏损限制属于明确的策略/账户政策；本次不新增自动强平处理进程。
- 粗数量步长可能让中性目标失衡或不可交易。已有组合预检必须在新增风险前拒绝不可行组合，
  不可悄悄提高单腿权重。修复阈值与允许偏差属于政策选择。
- 重启恢复依赖交易所真实状态和持久化订单身份。新的修复需要新的持久化 basket identity，
  恢复同一次修复则复用原身份，不能只用随运行目录变化而归零的计数器生成 ID。
- 长期行情采集需要有界查询、保留策略、新鲜度检查和内存监控。公开仓库没有生产行情采集
  进程可供本次修补，不能从这些执行组件推断出它已存在。
- 本地通过不等于实盘验收。先运行离线质量门禁，再审核具体账户集成并取得单独的执行授权。
  回归测试不会下真实订单或发送邮件。
