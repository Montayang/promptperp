# 投资人账本与报告子系统架构

状态：开发前设计
日期：2026-09-20

## 1. 目标与已确认边界

本子系统在一个共用的币安合约账户内维护多位投资人的经济权益，向交易系统提供只读的资金分配结果，并向投资人提供可审计的净值与回报报告。它不获得下单、撤单、调仓或修改账户的权限。

首版采用以下已确认规则：

- 投资人与策略池使用多对多份额关系；当前可以只持有一个共同池，未来通过空仓窗口中的按池申赎改变多策略配置。
- 任一受管仓位、未终结订单、未完成结算或对账阻断存在时，全局禁止入金和出金入账。
- 暂不计算管理费、业绩报酬或高水位线。
- 所有投资人共用一个币安合约账户，无法依靠子账户实现法律或技术隔离。
- 投资人邮件只能查询信息，不能更改配置、资金、策略或交易状态。
- 定期报告支持每日、每周、每月，并由操作员配置时区、发送时间和启用状态。
- 合规、合同、税务及客户身份管理不属于本仓库范围。

## 2. 核心原则

### 2.1 两类账本不能混用

交易执行账本负责证明 `strategy_id/run_id/intent_id/order_id` 的所有权和执行状态；投资人会计账本负责证明资金从哪里来、属于谁、当前有多少权益。执行事件只有经过成交归集和对账后，才能形成会计分录。

不得使用“币安钱包余额变化”直接代表某位投资人或某个策略的收益。钱包变化会混入手续费、资金费、人工交易、充值、提现以及其他策略结果。

### 2.2 账本是真相来源，快照只是视图

投资人余额必须由不可变的复式分录重放得到。净值快照、报表和邮件均是派生结果，可以重建，不能反向修改账本。更正错误时追加冲正分录，不覆盖历史记录。

### 2.3 明确的数值与时间语义

金额、份额、价格、费率和回报率使用十进制定点语义，不使用二进制浮点数。所有事件保存 UTC 时间；报告同时记录配置的展示时区。估值必须携带价格来源及时间戳，过期价格不能生成“已对账”的净值。

### 2.4 失败关闭

出现未知订单、外来仓位、成交归属不明、手续费或资金费无法分配、交易所权益与内部权益不一致、数据库事务失败或估值过期时：

- 禁止新的资金流和新策略分配；
- 报表标记为未对账，不发送确定性收益结论；
- 交易系统按既有安全规则决定是否同时禁止新开仓；
- 只允许操作员调查和追加可审计的修正，不允许自动抹平差额。

## 3. 会计模型

### 3.1 主体与策略池

- `Investor`：投资人身份及报告偏好；邮件地址属于受保护的个人信息。
- `StrategyPool`：同一策略版本、风险配置和计价币种下的资金池。
- `Subscription`：投资人与策略池之间的有效分配。首版每位投资人同时最多一个 100% subscription。
- `UnitLot`：投资人持有的策略池份额。资金进入时按当期确认净值申购份额，资金退出时赎回份额。
- `LedgerTransaction` / `LedgerEntry`：一个事务及其至少两条借贷平衡分录。
- `ValuationSnapshot`：某一截止时刻的策略池份额净值与投资人权益视图。

### 3.2 建议账户科目

首版至少需要投资人待分配资金、各策略池现金、已实现损益、未实现损益、交易手续费、资金费、投资人资本与累计收益，以及未归属差额和操作员调整。“未归属差额”不是正常收益账户；只要余额非零就触发对账阻断。

### 3.3 份额与净值

策略池总权益按同一估值截止点计算：

```text
pool_equity = allocated_cash
            + realized_pnl
            + unrealized_pnl
            - trading_fees
            + funding_pnl
            + explicit_adjustments

unit_nav = pool_equity / outstanding_units
investor_equity = investor_units * unit_nav
return_rate = investor_equity / net_contributed_capital - 1
```

申购和赎回使用已经对账并冻结的估值快照，不能使用稍后变化的价格回填。首笔申购可采用配置化初始单位净值，例如 `1 USDT`。零份额、负权益和精度余数必须有显式规则，不能静默丢失。

### 3.4 交易结果归属

交易系统向会计边界发布已确认事件，最少包含：

- strategy、run、intent、order、trade/fill 的稳定标识；
- symbol、方向、数量、成交价和事件时间；
- 已实现损益、手续费金额与资产；
- 资金费金额、结算时间和可证明的仓位归属；
- schema 版本、来源和幂等键。

会计消费者先验证事件所有权与幂等性，再在一个数据库事务中写入原始事件、会计事务和处理游标。重复事件不重复记账；乱序事件进入待处理状态；无法归属的事件进入阻断队列。

共享账户下同一 symbol、同一方向的多个策略仓位在交易所可能净额合并。因此，在执行层尚不能用成交和持仓精确证明策略所有权前，不允许两个策略同时共享该净额仓位。投资人账本不能用会计分摊掩盖交易层的所有权缺失。

## 4. 入金、出金与策略分配

资金流采用“申请—核验—过账”的操作流程，不直接监听到一笔链上或币安转账就自动改权益。

全局资金流门禁必须同时满足：

- 没有任何受管或外来持仓；
- 没有普通订单、条件单或保护单；
- 所有 execution intent 已到终态并完成会计结算；
- 最近一次交易所对账通过且未过期；
- 没有未知结果、未归属差额或人工调查事项；
- 资金流金额和外部转账证据已经操作员确认。

首版只允许在上述平仓窗口中进行申购、赎回和切换策略池。策略切换等价于旧池赎回和新池申购，必须留下两个相关但独立平衡的会计事务，不得修改历史 subscription。

## 5. 对账模型

每次生成正式快照前执行三层对账：

1. **事件对账**：每个交易所成交、手续费和资金费记录都有且只有一个自有执行事件和一个会计处理结果。
2. **仓位对账**：执行账本推导仓位与交易所仓位一致，不存在外来或无法证明所有权的仓位/订单。
3. **权益对账**：投资人权益、系统自有资金、保留项和未归属差额之和与交易所账户权益一致，允许的舍入阈值必须固定、很小且可审计。

每次对账保存输入截止点、交易所游标、账本序号、结果、差额和原因。报告只引用已经完成的 reconciliation ID。币安临时不可用时可以展示最近一次已对账快照及其时间，但不能把缓存值称作实时净值。

## 6. 邮件报告与只读查询

### 6.1 定期报告

每个投资人可配置 `daily`、`weekly` 或 `monthly`，以及时区和本地发送时间；月报还可配置每月 1 至 28 日的发送日。报告至少包含当前策略和版本、期初/期末权益、净资金流、区间和累计回报率、已实现/未实现损益、手续费、资金费、净值截止时间、对账状态和 reconciliation ID。组合报表完成前，多池投资人查询必须失败关闭而不是任选一个策略池。

调度任务只读取已生成的不可变报表，不在发送时临时查询币安。发送采用 outbox、唯一 delivery ID 和原子领取；明确未发送的失败才允许人工重试。SMTP 调用后结果不确定的消息保持 `SENDING` 并阻断自动重试，必须先向 provider 核验，且不得重复生成不同数字的同一期报告。

### 6.2 邮件实时查询

首版只接受有限白名单命令，例如 `净值`、`收益`、`策略`、`帮助`。回复读取最近的已对账快照，并明确其截止时间。

安全规则：

- 发件地址必须与投资人已验证地址精确匹配；
- 邮件正文不执行自然语言动作，不解析链接或附件，不接受转发邮件中的身份声明；
- 不支持入金、出金、策略切换、参数修改、下单、停机或任何管理动作；
- 每封来信按 provider message ID 去重，并限制频率；
- 日志隐藏完整邮箱、主题中的敏感文本和正文；
- 身份不匹配、命令未知或数据未对账时返回最少信息，不泄露其他投资人是否存在；
- 邮件通道被攻破最多只能读取该地址对应的有限报告，不能获得币安密钥或交易能力。

邮件收件处理器与交易运行器必须使用不同进程身份和凭据。收件处理器只获得报告只读存储权限；发件凭据不能访问投资人账本写接口。

## 7. 边界与事件流

```text
Binance read model ----> execution reconciliation
                              |
confirmed owned fills --------+
fees / funding ----------------+--> accounting ingest --> double-entry ledger
operator-confirmed cash flow --+                            |
                                                            v
                                                   valuation snapshot
                                                            |
                                          +-----------------+----------------+
                                          v                                  v
                                  scheduled statement                 read-only query
                                          |                                  |
                                          +------------ email outbox --------+
```

交易系统可以读取某策略池经对账的 `allocatable_equity`，但会计子系统不能调用下单接口。风险引擎仍决定实际可用保证金，并应用账户缓冲、上限和审批参数；账面权益不等于下单授权。

## 8. 数据保护、审计与备份

- 首版生产存储使用 Python 标准库支持的嵌入式 SQLite，不运行独立数据库服务。
- 只允许 accounting service 写入；定时记账、估值、报表和 outbox 任务在该进程内串行执行，邮件查询进程只读已发布快照。
- 启用外键、WAL、busy timeout、完整同步和事务边界；这些设置必须在启动时校验，不能依赖机器默认值。
- 一次业务动作涉及的 source event、复式分录、幂等键和处理游标必须在同一事务内提交。
- 备份使用 SQLite 在线备份 API 或经过验证的停写副本，禁止只复制正在写入的数据库主文件。
- 投资人 ID 使用不可猜测的内部标识；显示名和邮箱与交易事件分表保存。
- 生产数据库不提交仓库；示例和测试只用虚构人物与金额。
- 所有写操作带 actor、reason、correlation ID 和时间；操作员调整以后可扩展双人复核。
- 账本事务只追加，使用唯一约束、数据库事务和审计摘要检测篡改。
- 报告文件视为敏感数据，设置访问权限、保留期和删除策略；日志不记录完整报告。
- 备份必须加密，并定期验证能从备份重建余额和快照；恢复演练不能连接实盘接口。

选择 SQLite 是基于“小规模、单机、单写者”的已知条件，而不是降低会计不变量。客户和策略数量很少，但成交事件会长期累积，因此仍保留迁移、索引、归档和恢复测试。出现多主机写入、主动高可用、多个管理写入端、单写者持续成为瓶颈，或在线备份/查询无法满足运行目标时，必须先写新 ADR 再迁移到 PostgreSQL；不能在运行中临时共享 SQLite 文件。

## 9. 明确不在首版范围

- 一位投资人按比例同时投资多个策略；
- 管理费、业绩报酬、高水位线和税务报表；
- 投资人自助修改任何数据或交易配置；
- Web 门户、公开 API、即时价格流；
- 自动识别未声明的充值提现；
- 用内部账本解决交易所净仓位无法隔离的问题；
- 法律合同、KYC/AML、牌照和客户资金监管流程。

这些能力未来必须通过版本化迁移加入，不能改变既有历史分录的含义。

## 10. 关键验收不变量

实现阶段所有测试和评审至少证明：

- 每个会计事务借贷平衡且使用同一计价精度；
- 重放同一事件任意次数只产生一笔会计结果；
- 任意时点都能从分录重建投资人份额和策略池权益；
- 有持仓、订单、未结算事件或过期对账时，资金流必然被拒绝；
- 一个投资人的查询永远不能读取另一个投资人的信息；
- 邮件输入永远不能到达交易命令或账本写接口；
- 未对账或估值过期时不会发送带确定性“当前净值”的报告；
- 内部总权益与交易所权益差异超过阈值时系统阻断而非自动调账；
- 数据库崩溃、重复投递、乱序事件和邮件重复回调均不会产生重复分录或重复报告。
